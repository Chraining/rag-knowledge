## 0. 项目介绍话术

面试官通常会先说"介绍一下你的项目"，数据层部分可以这样讲（约 1 分钟）：

> 这是一个多用户的文档知识库，用户上传文档后可以针对自己的文档提问。数据层我用 PostgreSQL 加 SQLAlchemy 2.0，设计了六张表：用户、文档、文本段、会话、消息、使用记录。
>
> 设计上我重点考虑了几件事：第一是**权限隔离**，所有查询函数都在 SQL 层强制按 user_id 过滤，并且写了越权测试；第二是**索引**，我根据真实查询设计复合索引，造了一万条文档的数据用 EXPLAIN ANALYZE 对比，比如查会话消息有索引是 0.026 毫秒，没索引要 3 毫秒，全表扫描了 4 万行；第三是**N+1 问题**，会话列表要显示每个会话的最后一条消息，我用 LATERAL 子查询一条 SQL 搞定，并且写了测试统计 SQL 执行次数；第四是**幂等**，用文件内容哈希加唯一约束防止重复上传。
>
> 表结构用 Alembic 管理迁移，自动生成的迁移我审查时发现它把 CHECK 约束生成了两遍，手工修正了。

**要点**：讲具体数字、讲踩过的坑。面试官会顺着你说的点往下追问，所以只讲你能讲透的。

## 1. 规范里的六个设计问题

### 1.1 删除用户时，他的文档怎么办？级联删除还是禁止删除？

**答**：用户 → 文档用 `RESTRICT`（禁止删除），文档 → 文本段用 `CASCADE`（级联删除）。

- **为什么用户不级联**：
  1. 用户是**软删除**的（`is_active = false`），正常业务流程不会物理删除用户。物理删除应该是少见的、有意的操作（比如用户依法要求删除个人数据），所以数据库应该拦一下，防止误删。
  2. 文档在磁盘上有真实文件，数据库的级联删除只能删数据库里的行，删不掉磁盘文件。如果直接级联，会留下没有记录对应的"孤儿文件"。正确做法是应用代码先删文件、再删记录。
- **为什么文本段级联**：文本段是从文档"派生"出来的数据，文档没了，文本段没有任何意义，没有理由保留。会话 → 消息同理。

**追问**：`ON DELETE` 有哪几种？
- `CASCADE`：父行删了，子行一起删
- `RESTRICT` / `NO ACTION`：有子行时禁止删父行（两者区别：`NO ACTION` 可以推迟到事务结束再检查，`RESTRICT` 立即检查）
- `SET NULL`：父行删了，子行的外键设成 NULL（要求外键列可空）
- `SET DEFAULT`：设成默认值

**代码位置**：`app/models.py` 里每个 `ForeignKey(..., ondelete=...)`；测试 `test_user_with_documents_cannot_be_hard_deleted`、`test_deleting_document_deletes_its_chunks`。

### 1.2 `documents.user_id` 要不要加索引？怎么判断？不加会怎样？

**答**：要加。

- **怎么判断**：看真实查询。几乎所有对文档的查询都带 `WHERE user_id = ?`（列表、详情、按哈希查），这是最高频的过滤条件。
- **不加会怎样**：每次查询都要全表扫描。文档表有 100 万行时，查一个用户的 50 个文档也要读 100 万行。
- **我们的做法**：没有单独给 `user_id` 建索引，而是建了复合索引 `(user_id, created_at)`。它既能用于 `WHERE user_id = ?`（最左前缀），又能直接按时间顺序读出数据，省掉排序。
- **关键知识点**：**PostgreSQL 不会自动给外键列建索引**（MySQL InnoDB 会）。在 PG 里忘了给外键建索引是常见错误，后果有两个：按外键查询慢；删除父行时检查子表要全表扫描。

**实测**：去掉 `ix_documents_user_created` 后，PG 改用了 `uq_documents_user_hash` 这个唯一约束的索引（因为它也以 `user_id` 开头），但需要多一步 Sort 排序。

### 1.3 列出会话列表并显示每个会话的最后一条消息，怎么避免 N+1？

**答**：用 `LEFT JOIN LATERAL` 子查询，一条 SQL 完成。详见[第 6 节](#6-n1-问题)。

**代码位置**：`app/queries.py` 的 `list_conversations_with_last_message`；测试 `test_conversations_with_last_message_is_one_query` 断言只执行了 1 条 SQL。

### 1.4 上传文档：存文件 + 写记录 + 投递任务，中间失败怎么保证不留脏数据？

**答**：三个操作分属三个系统（文件系统、数据库、消息队列），**没有一个事务能同时覆盖它们**。只能靠合理的顺序和补偿。

**推荐顺序**：
1. 先计算哈希，查重（重复就直接返回已有文档）
2. 存文件到磁盘
3. 插入数据库记录并**提交**
   - 如果失败：删除第 2 步存的文件（补偿操作）
4. **提交之后**再投递任务
   - 如果失败：记录停在 `pending`，用定时任务扫描"长时间 pending"的文档重新投递

**为什么必须先提交再投递**：如果在事务里就投递任务，worker 可能比事务提交还快，去数据库查这个文档时查不到（事务还没提交，别的连接看不见）。

**为什么先存文件再写数据库**：反过来的话，数据库里有记录但文件可能没存成功，worker 处理时会找不到文件。"有文件没记录"比"有记录没文件"好处理——前者是垃圾，定期清理即可；后者是错误数据。

**进阶答案**：**Outbox 模式（事务性发件箱）**。在同一个数据库事务里，同时写文档记录和一条"待发送任务"记录到 outbox 表；另一个进程轮询 outbox 表并投递任务，投递成功后标记已发送。这样"写记录"和"要投递任务"在同一个事务里，保证一致。

**注意**：这部分是阶段 2、3 的内容，目前代码还没实现，但设计时要想清楚。

### 1.5 `content_hash` 是干什么的？同一个用户传了两次同样的文件怎么办？

**答**：`content_hash` 是文件内容的 SHA-256 哈希（64 位十六进制字符串）。内容相同，哈希一定相同。

- **用途一：去重**。`(user_id, content_hash)` 上有唯一约束，同一用户不能存两份相同内容。
- **用途二：幂等**。用户网络不好点了两次上传，或者前端重试，不会产生两条记录、两次解析、两份向量。
- **重复上传怎么处理**：接口直接返回已有文档的信息（通常返回 200 而不是 201），而不是报错。对用户来说，"我上传了这个文件，它在那里"这个结果是对的。
- **为什么是按用户唯一，而不是全局唯一**：不同用户上传同一份文件是正常的，而且他们的数据必须隔离。如果全局唯一，用户 B 上传时会发现"已存在"，这本身就泄露了"别人传过这个文件"的信息。

**追问**：为什么用 SHA-256 不用 MD5？
MD5 已经能被人为构造碰撞（两个不同文件哈希相同）。SHA-256 目前没有已知的碰撞方法，自然碰撞概率可以忽略。

**代码位置**：`app/models.py` 的 `UniqueConstraint("user_id", "content_hash")`；测试 `test_same_user_same_content_is_rejected`、`test_different_users_may_upload_same_content`。

### 1.6 统计今日配额的 `COUNT(*)` 在用户量上来后会不会慢？有什么替代方案？

**答**：

- **单次查询不慢**：我们的复合索引 `(user_id, action, created_at)` 正好对应查询条件，PG 用的是 **Index Only Scan**（只读索引不读表）。实测 0.044 毫秒，去掉索引后全表扫描 2 万行要 1.3 毫秒。
- **真正的问题是频率**：每次提问都要查一次。高并发下，大量这种查询会占用数据库连接和 CPU，而数据库是最难扩展的组件。
- **替代方案：Redis 计数器**
  ```
  INCR quota:{user_id}:{2026-10-13}      # 原子加一，返回加完后的值
  EXPIRE quota:{user_id}:{2026-10-13} 86400   # 第一次时设置过期时间
  ```
  返回值超过配额就拒绝（返回 429）。`INCR` 是原子操作，并发安全，而且在内存里，非常快。
- **追问：Redis 挂了怎么办？** 降级到数据库 COUNT 查询；或者暂时放行（宁可多给几次，也不要让服务不可用）。取决于业务对"超额"的容忍度。
- **追问：先 INCR 再检查，超额的那次也被计数了怎么办？** 可以接受（用户超额后反正被拒绝）；或者用 Lua 脚本把"检查 + 加一"做成原子操作。

**代码位置**：`app/queries.py` 的 `count_actions_since`；Redis 部分在阶段 4 实现。

## 2. 表设计

### 2.1 你的表之间是什么关系？

```
users ──1:N── documents ──1:N── chunks
  │
  ├──1:N── conversations ──1:N── messages
  │
  └──1:N── usage_logs
```

全部是**一对多**关系，外键放在"多"的一方。没有多对多关系（多对多需要中间表）。

### 2.2 为什么是这六张表？能不能少一张？

- `chunks` 不能合并进 `documents`：一个文档有几十上百段，检索的单位是段，不是文档。
- `messages` 不能合并进 `conversations`（比如存成 JSON 数组）：消息会不断追加，存在一个字段里每次都要重写整个数组；也没法按消息建索引和查询。
- `usage_logs` 理论上可以不要（直接在 users 上存今日计数），但那样就丢失了历史明细，没法做统计和审计。

### 2.3 你的设计满足第几范式？

- **第一范式（1NF）**：每列都是不可再分的原子值。`messages.sources` 是 JSON 数组，严格来说违反了 1NF，这是有意的取舍（见 2.5）。
- **第二范式（2NF）**：非主键列完全依赖于整个主键。我们都用单列自增主键，天然满足。
- **第三范式（3NF）**：非主键列不依赖于其他非主键列（没有传递依赖）。基本满足。
- **反范式的地方**：`documents.chunk_count` 是冗余的（可以用 `COUNT(*)` 从 chunks 表算出来），存它是为了列表页不用每次都统计。代价是要保证两者一致。

**面试要点**：范式不是越高越好。实际项目中常为了查询性能做有意的反范式，关键是能说出**为什么**以及**怎么保证一致性**。

### 2.4 `chunks` 为什么没有 `user_id`？

- **规范化的角度**：可以通过 `chunks.document_id → documents.user_id` 找到，存了就是冗余。
- **性能的角度**：阶段 4 做向量检索时，需要"只在当前用户的文本段里搜"。没有 `user_id` 就要 JOIN documents 表；有了就可以直接过滤，向量索引也更容易配合过滤条件。
- **结论**：阶段 4 很可能会有意加上（反范式）。如果用独立的向量数据库（如 Milvus），`user_id` 是必须存的，因为向量库没法 JOIN。

### 2.5 `sources` 为什么用 JSONB，而不是建一张 `message_sources` 关联表？

| | JSONB | 关联表 |
|---|---|---|
| 实现复杂度 | 简单，一个字段 | 多一张表、多一次 JOIN 或查询 |
| 读取 | 和消息一起读出，无需 JOIN | 需要 JOIN |
| 引用完整性 | **没有外键**，chunk 被删后变成悬空引用 | 有外键，可以 CASCADE 或 SET NULL |
| 反向查询（"哪些回答引用了这个 chunk"） | 困难（需要 GIN 索引） | 容易 |

**选择理由**：来源总是和消息一起展示，几乎不需要反向查询；而且来源是"历史快照"，记录的是"当时引用了什么"。

### 2.6 主键为什么用自增整数，不用 UUID？

| | 自增整数 | UUID |
|---|---|---|
| 大小 | 4 或 8 字节 | 16 字节 |
| 索引性能 | 顺序插入，B 树只在末尾追加，很快 | UUIDv4 随机，插入位置分散，造成索引页分裂和碎片 |
| 可猜测性 | 可以猜到别的 id（1, 2, 3...），能推算业务量 | 无法猜测 |
| 分布式生成 | 依赖数据库 | 任何地方都能生成，不冲突 |

**我们的情况**：所有查询都按 `user_id` 过滤，猜到别人的 id 也查不到数据，所以可猜测性不是安全问题，只是会暴露业务量。

**进阶**：**UUIDv7** 是按时间排序的 UUID，兼顾了"不可猜测"和"顺序插入"。PostgreSQL 18 已内置 `uuidv7()` 函数。

### 2.7 `users` 表为什么要 `is_active`？

用于**软删除**：注销用户时把 `is_active` 设成 `false`，而不是删除这一行。

- **好处**：数据可以恢复；保留历史记录用于审计；避免因外键关系导致的连锁删除。
- **坏处**：
  1. 所有查询都要记得加 `WHERE is_active`，忘了就会把已注销的用户查出来
  2. 已注销用户仍然占着唯一的用户名和邮箱（见[第 18 节](#18-本设计的已知不足)）
  3. 数据只增不减，表越来越大
  4. 某些法规（如个人信息保护法、GDPR）要求真正删除个人数据，软删除不够

### 2.8 `daily_quota` 为什么存在用户表上，而不是写在配置里？

不同用户可以有不同的配额（比如付费用户更多）。配置里的 `default_daily_quota` 只是新用户的默认值。

## 3. 数据类型与约束

### 3.1 `status` 为什么用 VARCHAR + CHECK，不用 PostgreSQL 原生 ENUM？

- **原生 ENUM**：`CREATE TYPE document_status AS ENUM (...)`。增加新值要 `ALTER TYPE ... ADD VALUE`（旧版本 PG 不能在事务里执行）；**删除或重命名值非常麻烦**，基本要重建类型。
- **VARCHAR + CHECK**：增删值只需要删掉旧约束、加上新约束，在普通迁移里就能完成。
- **代价**：每行多存几个字节（字符串而非 4 字节的枚举值），可以忽略。

**追问**：MySQL 的 ENUM 呢？MySQL 的 ENUM 修改值列表可能需要重建整张表，问题更大。

### 3.2 为什么时间用 `timestamptz`（带时区）？

- `timestamp`（不带时区）只存"年月日时分秒"，不知道是哪个时区的时间。服务器换了时区、或者多个服务器时区不同，数据就乱了。
- `timestamptz` 存的是一个**确切的时刻**（内部统一转成 UTC 存储），读取时按会话时区显示。
- **原则**：存储用 UTC，显示时再转成用户的本地时区。

### 3.3 `usage_logs.id` 为什么用 BigInteger？

它是增长最快的表：每次上传、提问都记一行。`Integer` 上限约 21 亿，假设 1 万用户每天各操作 100 次，约 6 年就会用完。到时候插入直接失败，修改主键类型需要重写整张表，代价极高。一开始就用 `BigInteger` 只是每行多 4 字节。

### 3.4 `VARCHAR(255)` 和 `TEXT` 在 PostgreSQL 里有性能区别吗？

**没有**。PG 里 `VARCHAR(n)`、`TEXT` 底层存储完全一样，`VARCHAR(n)` 只是多了一个长度检查。所以用 `VARCHAR(n)` 是为了**业务约束**（比如用户名不能太长），不是为了性能。

（MySQL 不同：`VARCHAR` 和 `TEXT` 存储方式不同，`TEXT` 不能有默认值，建索引要指定前缀长度。）

### 3.5 JSON 和 JSONB 有什么区别？

| | JSON | JSONB |
|---|---|---|
| 存储 | 原样存文本 | 解析后存二进制 |
| 写入 | 快（不解析） | 稍慢（要解析） |
| 读取 / 查询 | 慢（每次都要解析） | 快 |
| 保留格式 | 保留空格、键顺序、重复键 | 不保留 |
| 索引 | 不支持 | 支持 GIN 索引 |

**结论**：除非需要保留原始格式，否则一律用 JSONB。

### 3.6 `default` 和 `server_default` 有什么区别？

- `default`：SQLAlchemy 在 Python 里插入时填的默认值。**用原生 SQL 插入时不生效**。
- `server_default`：写进了表定义（`DEFAULT ...`），由数据库填充，**任何方式插入都生效**。
- 我们两个都写了：`server_default` 保证数据库层面的正确性；`default` 让 Python 对象在 flush 之前就有值。

### 3.7 `messages.created_at` 为什么用 `clock_timestamp()` 而不是 `now()`？

**这是一个很好的加分点。**

- `now()`（等同于 `transaction_timestamp()`）返回的是**当前事务开始的时间**，同一个事务里调用多少次都一样。
- 保存一问一答时，用户消息和 AI 回答通常在同一个事务里写入，用 `now()` 的话两条消息时间**完全相同**，按时间排序就分不出先后。
- `clock_timestamp()` 返回**真实的当前时间**，每次调用都不同。
- 查询时我们还加了 `id` 作为第二排序键（`ORDER BY created_at, id`），双重保险。

### 3.8 约束应该放在数据库里，还是放在应用代码里？

**都要，但数据库约束是最后一道防线。**

- 应用代码检查：能给用户友好的错误提示。
- 数据库约束：保证**无论数据从哪里来**（应用 bug、手工 SQL、另一个服务、并发竞争）都不会存入非法数据。
- 典型例子：并发上传时，"先查再插"的应用检查会失效（见 7.5），只有唯一约束能真正保证不重复。

**我们用到的约束**：主键、外键、唯一约束（用户名、邮箱、用户+哈希、文档+段号）、CHECK 约束（状态值、文件大小非负）、NOT NULL。

### 3.9 唯一约束里的列可以是 NULL 吗？

可以。PG 默认把每个 NULL 当成互不相等，所以唯一列里可以有多个 NULL。PG 15 起可以用 `UNIQUE NULLS NOT DISTINCT` 让多个 NULL 也算重复。

## 4. 索引

### 4.1 索引是什么？原理是什么？

索引是一个独立于表的、**有序的**数据结构，存着"列的值 → 行的位置"。就像书的目录：不用一页页翻，直接查目录找到页码。

- PG 和 MySQL 默认的索引都是 **B+ 树**（PG 文档里叫 B-tree，实现上是 B+ 树的变体）。
- 查找复杂度是 O(log n)。100 万行数据，B+ 树大约 3～4 层，只需要读 3～4 个页。
- **B+ 树的特点**：数据只存在叶子节点，叶子节点之间用链表连起来，所以**范围查询和排序**也很快（找到起点后顺着链表读）。

### 4.2 为什么是 B+ 树，不是哈希表或二叉树？

- **哈希表**：等值查询 O(1)，但**不支持范围查询和排序**（`created_at >= 今天`、`ORDER BY` 都用不上）。
- **二叉树**：每个节点只有两个分支，树太高，每层都要读一次磁盘。
- **B 树**：每个节点都存数据，范围查询要在树里来回跳。
- **B+ 树**：一个节点有几百个分支，树很矮；叶子链表让范围扫描很快。

（PG 也支持哈希索引，只适用于等值查询，很少用。）

### 4.3 什么是最左前缀原则？

复合索引 `(a, b, c)` 是先按 `a` 排序，`a` 相同再按 `b`，`b` 相同再按 `c`。所以：

| 查询条件 | 能否用上索引 |
|---|---|
| `WHERE a = ?` | 能 |
| `WHERE a = ? AND b = ?` | 能 |
| `WHERE a = ? AND b = ? AND c = ?` | 能 |
| `WHERE a = ? ORDER BY b` | 能，而且不用额外排序 |
| `WHERE b = ?` | **不能**（跳过了 a） |
| `WHERE a = ? AND c = ?` | 只能用上 a 部分 |

**项目实例**：去掉 `ix_documents_user_created (user_id, created_at)` 后，PG 自动改用 `uq_documents_user_hash (user_id, content_hash)`，因为它也以 `user_id` 开头。但这个索引里同一用户的文档是按哈希排的，不是按时间，所以多了一步 Sort。

### 4.4 复合索引的列顺序怎么定？

**等值条件的列放前面，范围条件或排序的列放最后。**

以配额查询为例：`WHERE user_id = ? AND action = ? AND created_at >= ?`
- `user_id`、`action` 是等值，放前面
- `created_at` 是范围，放最后
- 所以是 `(user_id, action, created_at)`

如果顺序是 `(created_at, user_id, action)`，范围条件在最前面，索引只能用来定位时间范围，范围内所有用户的记录都要逐条检查。

**另一个原则**：区分度高的列放前面（区分度 = 不同值的数量 / 总行数）。但"等值在前，范围在后"优先。

### 4.5 什么是覆盖索引 / 仅索引扫描（Index Only Scan）？

如果查询需要的**所有列都在索引里**，数据库只读索引就能得到结果，完全不用读表。

**项目实例**：配额查询 `SELECT count(*) FROM usage_logs WHERE user_id=? AND action=? AND created_at>=?`，三个条件列都在索引里，count 不需要其他列。EXPLAIN 显示 `Index Only Scan`，`Heap Fetches: 0`（没读表）。

- MySQL 里叫**覆盖索引**，可以避免"回表"。
- PG 的特殊之处：还要检查"可见性映射（visibility map）"确认行对当前事务可见。如果表最近被大量修改且还没 VACUUM，仍需回表检查（`Heap Fetches` 会大于 0）。

### 4.6 唯一约束和唯一索引是什么关系？

在 PG 里，创建唯一约束会**自动创建一个唯一索引**来实现它。所以：
- `chunks` 的 `UNIQUE (document_id, chunk_index)` 自带一个以 `document_id` 开头的索引，**不需要再单独给 `document_id` 建索引**。
- `users` 的 `username`、`email` 唯一约束也自带索引，登录时按用户名查找很快。

### 4.7 为什么 `chunks.document_id` 的索引对删除也很重要？

删除一个文档时，`ON DELETE CASCADE` 要找出这个文档的所有 chunks 去删。没有 `document_id` 的索引，就要**全表扫描整个 chunks 表**。chunks 是数据量最大的表之一，每删一个文档都扫一遍会很慢。

同理，`RESTRICT` 删除用户时也要检查子表有没有引用它的行，没有索引也要全表扫描。

### 4.8 为什么不给 `status` 建索引？

- `status` 只有 4 个值，**区分度很低**。比如查 `status = 'ready'` 可能命中一半以上的行，用索引还要来回跳着读表，不如直接全表扫描。
- **更好的方案：部分索引（Partial Index）**。阶段 3 的 worker 需要找"待处理"的文档，而这种文档通常很少：
  ```sql
  CREATE INDEX ix_documents_pending ON documents (created_at) WHERE status = 'pending';
  ```
  索引只包含 pending 的行，非常小，查询很快。

### 4.9 索引有什么代价？是不是越多越好？

**不是。**
1. **写入变慢**：每次 INSERT、UPDATE、DELETE 都要同时更新所有相关索引。
2. **占用空间**：索引可能和表本身一样大。
3. **影响优化器**：索引太多，优化器选择计划的时间变长，也可能选错。

**原则**：只为真实的、高频的查询建索引，并用 EXPLAIN 验证它确实被用上了。我们每个索引都对应一个具体的查询函数。

### 4.10 什么情况下有索引也用不上？

1. **对列做了运算或函数**：`WHERE lower(email) = ?`、`WHERE created_at + interval '1 day' > now()`。解决：改写查询，或建**表达式索引** `CREATE INDEX ON users (lower(email))`。
2. **违反最左前缀**：见 4.3。
3. **隐式类型转换**：列是字符串，传入的是数字。
4. **前缀模糊匹配**：`LIKE '%abc'` 用不上普通索引（`LIKE 'abc%'` 可以）。
5. **`OR` 条件**：`WHERE a = 1 OR b = 2`，可能退化成全表扫描。
6. **优化器判断全表扫描更便宜**：表很小，或者命中的行太多（见 5.4）。

### 4.11 JSONB 字段能建索引吗？

能，用 **GIN 索引**（倒排索引）：
```sql
CREATE INDEX ON messages USING GIN (sources);
-- 可加速：WHERE sources @> '[{"chunk_id": 123}]'
```
GIN 索引适合"包含"类查询（JSONB、数组、全文搜索）。

### 4.12 什么是聚簇索引？PG 有吗？

- **聚簇索引**：表数据本身按某个索引的顺序存储。MySQL InnoDB 的主键就是聚簇索引，数据直接存在主键 B+ 树的叶子节点里。
- **PG 没有聚簇索引**：表数据存在独立的"堆（heap）"里，没有固定顺序；所有索引都是"二级索引"，叶子节点存的是行在堆里的物理位置（ctid）。
- PG 有一个 `CLUSTER` 命令，可以按某个索引**一次性**重排表数据，但之后新插入的数据不会保持这个顺序。

## 5. EXPLAIN 与查询优化

### 5.1 EXPLAIN 和 EXPLAIN ANALYZE 有什么区别？

- `EXPLAIN`：只显示优化器**打算**怎么执行，以及它**估计**的成本和行数。不执行查询。
- `EXPLAIN ANALYZE`：**真正执行**查询，显示**实际**耗时和行数。
- `EXPLAIN (ANALYZE, BUFFERS)`：额外显示读了多少数据页（`shared hit` 是缓存命中，`read` 是从磁盘读）。

**注意**：`EXPLAIN ANALYZE DELETE ...` 会**真的删除数据**！要放在事务里执行然后回滚。

### 5.2 怎么读 EXPLAIN 的结果？

1. **从最里层（缩进最深）往外读**，里层先执行。
2. **看扫描方式**：
   - `Seq Scan`：全表扫描，大表上通常是问题信号
   - `Index Scan`：用索引找到行，再去表里读
   - `Index Only Scan`：只读索引
   - `Bitmap Index Scan` + `Bitmap Heap Scan`：先用索引找出所有匹配行的位置，排好序后批量读表（命中行较多时用）
3. **看有没有 `Sort`**：有的话说明没能利用索引的顺序。
4. **对比 `rows`（估计）和 `actual rows`（实际）**：差距很大说明统计信息过时，需要 `ANALYZE`。
5. **看 `Rows Removed by Filter`**：读了又扔掉的行，越多越浪费。

### 5.3 你实测的结果是什么？

数据量：1 万文档、4 万消息、2 万使用记录。

| 查询 | 有索引 | 无索引 |
|---|---|---|
| 一个会话的消息 | 0.026 ms，Index Scan | 2.99 ms，Seq Scan，`Rows Removed by Filter: 39980` |
| 今日配额计数 | 0.044 ms，Index Only Scan | 1.32 ms，Seq Scan，过滤掉 2 万行 |
| 用户文档列表 | Index Scan Backward，直接读 20 行，无排序 | 用了另一个索引，读 50 行再 Sort |

**说明**：数据量还小，绝对时间差距不大；但全表扫描的耗时随数据量**线性增长**，而索引查询几乎不变。数据量大 100 倍时，差距也会大约 100 倍。

### 5.4 为什么表里有索引，优化器却选择了全表扫描？

1. **表很小**：几百行的表，全表扫描只读几个页，比走索引还快。所以测试 EXPLAIN 一定要造足够的数据（我们的 seed 脚本就是为此写的）。
2. **命中行太多**：要返回表中 30% 以上的行时，走索引要来回随机读，不如顺序读整张表。
3. **统计信息过时**：优化器以为表很小。解决：`ANALYZE`（我们的 seed 脚本最后会执行）。
4. 以及 4.10 列出的"索引用不上"的情况。

### 5.5 你是怎么安全地测试"没有索引"的情况的？

PostgreSQL 的 **DDL（建表、删索引等）支持事务**。所以 `scripts/explain.py` 的做法是：
1. 开启事务
2. 执行 EXPLAIN ANALYZE（有索引）
3. `DROP INDEX`
4. 再执行 EXPLAIN ANALYZE（无索引）
5. **回滚事务**——索引恢复原样

MySQL 做不到，因为 MySQL 的 DDL 会**隐式提交**当前事务，无法回滚。

**注意**：`DROP INDEX` 会对表加排他锁，事务没结束前其他查询都会被阻塞。所以只能在开发环境这样做，不能在生产环境做。

### 5.6 怎么找出系统里的慢查询？

1. **`pg_stat_statements` 扩展**：统计每类 SQL 的执行次数、总耗时、平均耗时，找出"总耗时最多"的查询（不一定是单次最慢的，可能是执行次数最多的）。
2. **慢查询日志**：设置 `log_min_duration_statement = 200`，超过 200 毫秒的查询写入日志。
3. **应用层监控**：在 SQLAlchemy 里监听查询事件记录耗时（阶段 5 的结构化日志会做）。

## 6. N+1 问题

### 6.1 什么是 N+1 问题？

先用 1 条查询拿到 N 条记录，再对每条记录各发 1 条查询获取关联数据，总共 N+1 条查询。

```python
# 错误写法：N+1
convs = db.scalars(select(Conversation).where(Conversation.user_id == uid))  # 1 条
for c in convs:
    last = db.scalar(                                                         # N 条
        select(Message).where(Message.conversation_id == c.id)
        .order_by(Message.created_at.desc()).limit(1)
    )
```

会话列表有 20 个会话就是 21 条查询。每条查询都有网络往返的开销，即使每条只要 1 毫秒，加起来也很慢。

### 6.2 ORM 为什么容易产生 N+1？

ORM 的关系默认是**懒加载（lazy loading）**：访问 `conversation.messages` 时才发查询。在循环里访问关系属性，就会悄悄地产生 N 条查询，代码上完全看不出来。

### 6.3 有哪些解决方法？

| 方法 | 查询次数 | 说明 |
|---|---|---|
| **LATERAL JOIN**（我们用的） | 1 | 对每个会话执行一次子查询取最新消息，每次都走索引 |
| `DISTINCT ON` | 1 | PG 特有：`SELECT DISTINCT ON (conversation_id) * FROM messages ORDER BY conversation_id, created_at DESC` |
| 窗口函数 `ROW_NUMBER()` | 1 | `ROW_NUMBER() OVER (PARTITION BY conversation_id ORDER BY created_at DESC)`，取等于 1 的行。MySQL 8 也支持 |
| `selectinload` | 2 | 先查会话，再用 `WHERE conversation_id IN (...)` 一次查出所有消息。但会把**所有**消息都查出来，不只是最后一条 |
| `joinedload` | 1 | 用 JOIN 一次查出，同样会查出所有消息，数据量大时结果集膨胀 |
| 冗余字段 | 1 | 在会话表上存 `last_message_id` 或 `last_message_preview`，写消息时同步更新。读最快，但写入复杂 |

### 6.4 为什么选 LATERAL？

- 只取每个会话的**一条**消息，不会把所有消息都查出来（`selectinload` 和 `joinedload` 会）。
- 子查询 `WHERE conversation_id = ? ORDER BY created_at DESC LIMIT 1` 正好能用上 `(conversation_id, created_at)` 索引，每次只读一个索引条目。
- 只取 20 个会话时，就只执行 20 次子查询；`DISTINCT ON` 和窗口函数则可能要处理该用户的全部消息。

### 6.5 你怎么证明没有 N+1？

写测试统计 SQL 执行次数。`tests/test_queries.py` 里的 `CountQueries` 类监听 SQLAlchemy 的 `before_cursor_execute` 事件，每执行一条 SQL 计数加一。测试创建了 4 个会话（分别有 3、1、0、5 条消息），断言：
1. 只执行了 **1 条** SQL
2. 每个会话的最后一条消息都正确，**没有消息的会话也在结果里**（`LEFT JOIN` 的作用）

**这个测试的价值**：以后有人改代码不小心引入 N+1，测试会立刻失败。

## 7. 事务、并发与锁

### 7.1 什么是 ACID？

- **A 原子性（Atomicity）**：事务里的操作要么全部成功，要么全部失败回滚。
- **C 一致性（Consistency）**：事务前后，数据都满足所有约束（外键、唯一、CHECK 等）。
- **I 隔离性（Isolation）**：并发执行的事务互不干扰，看不到对方未提交的修改。
- **D 持久性（Durability）**：事务一旦提交，即使数据库崩溃，数据也不会丢（靠预写日志 WAL 保证）。

**项目实例**：`scripts/seed.py` 用 `with SessionLocal.begin()` 包住所有插入，中途任何一步出错都会全部回滚，不会留下"有用户没文档"的半成品数据。

### 7.2 事务隔离级别有哪些？各解决什么问题？

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 不会 | 可能 | 可能 |
| 可重复读（Repeatable Read） | 不会 | 不会 | 可能（标准）/ PG 和 InnoDB 基本不会 |
| 串行化（Serializable） | 不会 | 不会 | 不会 |

- **脏读**：读到了别的事务**还没提交**的数据（对方回滚后，你读到的就是不存在的数据）。
- **不可重复读**：同一事务里两次读**同一行**，结果不一样（中间被别人修改并提交了）。
- **幻读**：同一事务里两次执行**同一个范围查询**，结果的行数不一样（中间被别人插入了新行）。

**默认级别**：PostgreSQL 是**读已提交**；MySQL InnoDB 是**可重复读**。
**PG 的特殊之处**：PG 的"读未提交"实际表现和"读已提交"一样，不会出现脏读。

### 7.3 什么是 MVCC？

**多版本并发控制**。修改一行时不直接覆盖，而是保留旧版本、生成新版本。每个事务根据自己的"快照"决定能看到哪个版本。

- **好处**：**读不阻塞写，写不阻塞读**。读操作不需要加锁。
- **PG 的实现**：旧版本直接留在表里，需要 `VACUUM` 定期清理死元组（autovacuum 会自动做）。表频繁更新时会"膨胀"。
- **MySQL InnoDB 的实现**：表里只有最新版本，旧版本存在 undo log 里。

### 7.4 文档状态从 pending 改成 processing，并发时怎么保证只有一个 worker 处理？

阶段 3 会遇到。两种方案：

**方案一：乐观更新（条件更新）**
```sql
UPDATE documents SET status = 'processing'
WHERE id = ? AND status = 'pending';
```
检查受影响的行数：等于 1 说明抢到了，等于 0 说明别人已经在处理了。数据库保证同一行的 UPDATE 是串行的。这也是**状态机**的正确实现方式：只允许从合法的旧状态转换到新状态。

**方案二：悲观锁**
```sql
SELECT * FROM documents WHERE status = 'pending'
ORDER BY created_at LIMIT 1
FOR UPDATE SKIP LOCKED;
```
`FOR UPDATE` 锁住选中的行；`SKIP LOCKED` 跳过已被别人锁住的行。多个 worker 同时执行会各拿到不同的文档，这是用数据库实现任务队列的经典写法。

### 7.5 两个相同的上传请求同时到达会怎样？

如果代码是"先查哈希是否存在，不存在再插入"：

```
请求 A：查询哈希 → 不存在
请求 B：查询哈希 → 不存在       （A 还没插入）
请求 A：插入 → 成功
请求 B：插入 → ？
```

这就是**竞态条件（race condition）**，"先检查后操作"在并发下不安全。

- **唯一约束是最后一道防线**：请求 B 的插入会违反 `(user_id, content_hash)` 唯一约束而失败，数据库保证了不会有重复。
- **应用要处理这个错误**：捕获 `IntegrityError`，然后查出已有的文档返回给用户。
- **或者用 upsert**：`INSERT ... ON CONFLICT (user_id, content_hash) DO NOTHING RETURNING id`，没插入就再查一次。

### 7.6 什么是死锁？怎么避免？

两个事务互相等待对方持有的锁：
```
事务 1：锁住 A → 等待 B
事务 2：锁住 B → 等待 A
```
数据库会检测到死锁，强制回滚其中一个事务。

**避免方法**：
1. **所有事务按相同顺序加锁**（比如都按 id 从小到大）
2. 事务尽量短，尽快提交
3. 不要在事务里做慢操作（调用外部 API、等待用户输入）——**这一条对本项目很重要**：调用 LLM 或 embedding API 可能要几十秒，绝不能放在数据库事务里

### 7.7 为什么不能在数据库事务里调用 LLM API？

事务期间会一直占用一个数据库连接，还可能持有行锁。LLM 调用可能要 10～60 秒：
- 连接池很快被耗尽，其他请求都在排队
- 持有的锁阻塞其他事务
- 长事务让 PG 的 VACUUM 无法清理旧版本数据

**正确做法**：先在一个短事务里读出需要的数据并提交，然后调用 API，最后再开一个短事务写入结果。

## 8. ORM 与 SQLAlchemy

### 8.1 为什么用 ORM？ORM 有什么缺点？

**优点**：
- 用 Python 对象操作数据，不用手写大量 SQL
- 防止 SQL 注入（参数自动绑定）
- 模型定义就是文档，可以配合迁移工具自动生成表结构变更

**缺点**：
- 容易写出低效查询（N+1 是最典型的）
- 生成的 SQL 不直观，需要打印出来检查
- 复杂查询（窗口函数、LATERAL、CTE）用 ORM 写反而更绕

**我们的做法**：模型和简单查询用 ORM，复杂查询（如会话列表）仍然用 SQLAlchemy 的表达式构造，并打印 SQL 检查结果。

### 8.2 SQLAlchemy 2.0 和 1.x 写法有什么区别？

- **查询**：1.x 用 `session.query(User).filter(...)`；2.0 用 `select(User).where(...)`，然后 `session.scalars(stmt)` 执行。查询语句和执行分离，ORM 和 Core 的写法统一了。
- **模型定义**：2.0 用 `Mapped[int]` 类型标注 + `mapped_column()`，可以被类型检查工具识别；`Mapped[str | None]` 自动表示可空。
- **事务**：2.0 默认"自动开始"事务，必须显式 commit。

### 8.3 Engine、连接池、Session 分别是什么？

- **Engine**：数据库的入口，管理**连接池**。整个应用只创建一个（`app/db.py`）。
- **连接池**：预先建好一些数据库连接反复使用。建立 PG 连接要经过 TCP 握手、认证、启动后端进程，大约需要几毫秒到几十毫秒，比一次简单查询还慢。
- **Session**：一次"工作单元"，跟踪你加载和修改的对象，最后一起提交。**Session 不是线程安全的**，每个请求要用自己的 Session。

**追问：FastAPI 里怎么管理 Session？** 用带 `yield` 的依赖：
```python
def get_db():
    with SessionLocal() as db:
        yield db
```
每个请求得到一个新 Session，请求结束自动关闭。（阶段 2 会写）

### 8.4 `flush()` 和 `commit()` 有什么区别？

- `flush()`：把 Session 里待执行的修改**发送给数据库执行**（INSERT、UPDATE），但**不提交事务**。执行后能拿到数据库生成的 id，但别的连接还看不到这些数据，回滚后也会消失。
- `commit()`：先 flush，再**提交事务**，修改永久生效，对其他连接可见。

**项目实例**：测试里的 `make_user` 调用 `db.flush()` 拿到 `user.id`，但不提交，测试结束后整个事务回滚。

### 8.5 `expire_on_commit=False` 有什么用？

默认 `True` 时，commit 之后 Session 会把所有对象标记为"过期"，下次读属性时重新从数据库查。这是为了防止读到旧数据，但会带来额外查询；在 FastAPI 里，commit 后返回对象给前端时还可能因为 Session 已关闭而报错。设成 `False` 后，commit 后属性仍保持原值可读。

### 8.6 `cascade="all, delete-orphan"` 和 `passive_deletes=True` 是什么？

- `cascade="all, delete-orphan"`：ORM 层面的级联。在 Python 里删除文档时，ORM 也会处理它的 chunks；从 `document.chunks` 列表里移除一个 chunk，这个 chunk 会被删除（"孤儿"删除）。
- `passive_deletes=True`：删除文档时，ORM **不先把 chunks 查出来逐个删除**，而是信任数据库的 `ON DELETE CASCADE` 去做。一个文档有几百个 chunks 时，能省掉几百条 DELETE。

**项目里的测试**：`test_deleting_document_deletes_its_chunks` 故意用 Core 的 `delete()` 语句（绕过 ORM 级联），证明是**数据库层面**的 CASCADE 在起作用。

### 8.7 懒加载有哪些策略？

| 策略 | 什么时候查 | 查询方式 |
|---|---|---|
| `select`（默认懒加载） | 第一次访问属性时 | 每个对象一条查询 → 容易 N+1 |
| `selectinload` | 查主对象时立即加载 | 额外一条 `WHERE id IN (...)` |
| `joinedload` | 查主对象时立即加载 | 用 JOIN 合并成一条查询 |
| `raiseload` | 禁止懒加载 | 访问时直接报错，用来**发现** N+1 |

### 8.8 什么是 Identity Map（标识映射）？

同一个 Session 里，同一行数据只对应**一个** Python 对象。查两次 id=1 的用户，得到的是同一个对象（`a is b` 为 True）。这保证了在一个 Session 里修改对象时不会出现两个版本互相覆盖。

### 8.9 ORM 怎么防止 SQL 注入？

ORM 生成的 SQL 用的是**参数绑定**：SQL 语句和参数值分开发送给数据库，参数值永远被当作数据，不会被当作 SQL 执行。

```python
# 安全：参数绑定
text("SELECT * FROM users WHERE id = :id"), {"id": user_input}
# 危险：字符串拼接
text(f"SELECT * FROM users WHERE id = {user_input}")
```

**注意**：`scripts/explain.py` 里用了 f-string 拼 SQL，这是可以接受的，因为拼进去的是代码里写死的常量，不是用户输入。

## 9. 数据库迁移

### 9.1 为什么用 Alembic，不直接用 `create_all()`？

- `Base.metadata.create_all()` 只会创建**不存在的表**，不会修改已有的表（加列、改类型、加索引都做不到）。
- 生产环境里表已经有数据了，改表结构必须用迁移：
  - **有版本号**：知道数据库现在是哪个版本
  - **可审查**：迁移文件进 git，能 code review
  - **可回滚**：每个迁移都有 `downgrade()`
  - **各环境一致**：开发、测试、生产执行同一套迁移

### 9.2 Alembic 自动生成的迁移能直接用吗？

**不能，必须人工审查。**

**项目里的真实例子**：自动生成的迁移把每个枚举的 CHECK 约束都生成了**两遍**（同名），PG 会拒绝执行。原因是 `sa.Enum(create_constraint=True)` 本身会生成约束，Alembic 又从元数据里单独生成了一遍。我手工把列改成 `sa.String(20)`，只保留一个 CHECK 约束。

**自动生成的其他已知局限**：
1. **识别不了重命名**：列或表改名，它会生成"删除旧列 + 新增新列"，**数据会丢失**
2. 识别不了某些类型变化、约束变化
3. 不处理数据迁移（比如把旧字段的值转换后填入新字段）

### 9.3 你怎么验证迁移是正确的？

1. `alembic upgrade head`：升级成功
2. `alembic downgrade base`：能回滚
3. 再次 `alembic upgrade head`：回滚后能重新升级
4. `alembic check`：确认模型定义和数据库实际结构**完全一致**（输出 "No new upgrade operations detected"）
5. 测试的 fixture 用**真实的迁移**建表（而不是 `create_all`），每次跑测试都在验证迁移

### 9.4 怎么在不停机的情况下给生产环境的大表加索引？

普通的 `CREATE INDEX` 会**阻塞写入**直到索引建完，大表可能要几分钟甚至几小时。

用 `CREATE INDEX CONCURRENTLY`：
- 不阻塞读写
- 代价：建得更慢；**不能在事务里执行**；失败会留下一个无效索引，需要手动删除
- Alembic 里要用 `with op.get_context().autocommit_block():` 包起来

### 9.5 怎么安全地给大表加一个 NOT NULL 列？

- **PG 11 之后**：`ALTER TABLE ... ADD COLUMN x INT NOT NULL DEFAULT 0` 很快，只改表定义，不重写数据（默认值必须是常量）。
- **更通用的安全做法（分多步）**：
  1. 加一个可空的列
  2. 代码开始写入新列
  3. 分批回填历史数据（避免一次更新几百万行导致长事务和锁）
  4. 加上 NOT NULL 约束

### 9.6 迁移和代码部署的顺序是什么？

原则：**数据库变更要和新旧两版代码都兼容。**
- **加列**：先迁移，再部署代码（旧代码不知道新列，不受影响）
- **删列**：先部署不再使用该列的代码，再迁移删列（否则旧代码会报错）
- **改名**：拆成"加新列 → 双写 → 迁移数据 → 切换读取 → 删旧列"多步

## 10. 权限隔离

### 10.1 怎么保证用户只能看到自己的文档？

**每个查询函数都接收 `user_id` 参数，并在 SQL 的 WHERE 里过滤。**

```python
select(Document).where(Document.id == document_id, Document.user_id == user_id)
```

**代码位置**：`app/queries.py` 顶部的文档字符串写明了这条规则；所有函数都遵守。

### 10.2 为什么不能"先查出来再判断是不是自己的"？

```python
# 错误写法
doc = db.get(Document, document_id)
if doc.user_id != current_user.id:
    raise Forbidden()
```

1. **容易漏**：项目里有几十个查询，只要一处忘了写判断就是越权漏洞。在 SQL 里过滤是"默认安全"。
2. **列表查询没法这样做**：查列表时要先查出所有人的数据再在 Python 里过滤，既不安全又低效。
3. **复杂查询更容易出错**：比如 JOIN 了多张表，只检查了一张表的归属。

### 10.3 拿到别人的 `document_id`，能查到内容吗？

**不能。** 查询条件是 `WHERE id = ? AND user_id = ?`，id 对得上但 user_id 对不上，结果为空。

**追问：应该返回 403 还是 404？**
- 我们的查询函数对"不存在"和"不是你的"都返回 `None`，无法区分。
- 返回 **404** 更安全：如果"不是你的"返回 403、"不存在"返回 404，攻击者就能通过遍历 id 探测出"哪些 id 存在"。
- 规范里写的是 403，两种都有人用，关键是能说出理由。

**测试**：`test_get_document_of_other_user_returns_none`、`test_list_messages_of_other_users_conversation_is_empty` 等。

### 10.4 messages 表没有 `user_id`，怎么做权限过滤？

JOIN `conversations` 表，按 `conversations.user_id` 过滤：
```python
select(Message)
.join(Conversation, Message.conversation_id == Conversation.id)
.where(Conversation.id == conversation_id, Conversation.user_id == user_id)
```

### 10.5 还有没有更强的隔离方式？

**PostgreSQL 行级安全（Row Level Security, RLS）**：
```sql
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
CREATE POLICY user_isolation ON documents
    USING (user_id = current_setting('app.user_id')::int);
```
每个请求开始时设置 `SET app.user_id = 123`，之后**数据库自动**给所有查询加上过滤条件，应用代码忘了写也不会越权。

**代价**：增加复杂度，调试更难，要小心连接池复用时残留的设置。多租户 SaaS 常用这种方式。

## 11. 幂等与去重

### 11.1 什么是幂等？

**同一个操作执行一次和执行多次，结果相同。**

- `GET`、`PUT`、`DELETE` 天然幂等；`POST` 通常不幂等。
- 为什么重要：网络超时后客户端会重试，消息队列可能重复投递任务。如果操作不幂等，就会产生重复数据。

### 11.2 本项目哪些地方需要幂等？怎么实现的？

| 场景 | 实现方式 |
|---|---|
| 同一用户重复上传同一文件 | `(user_id, content_hash)` 唯一约束 |
| 同一文档被重复处理（任务重复投递） | `(document_id, chunk_index)` 唯一约束，重复插入 chunk 会失败 |
| 状态转换 | 条件更新 `WHERE status = 'pending'`（阶段 3） |

### 11.3 文档处理任务失败后重试，会不会产生重复的 chunks？

有唯一约束 `(document_id, chunk_index)`，重复插入会直接报错，不会产生重复数据。但更好的做法是，**重新处理前先删掉这个文档的旧 chunks**，在同一个事务里"删旧 + 插新"，这样不管上次失败在哪一步，结果都一样。（阶段 3 实现）

## 12. 配额计数

### 12.1 配额查询怎么写的？

```sql
SELECT count(*) FROM usage_logs
WHERE user_id = ? AND action = 'query' AND created_at >= 今天零点
```

**代码位置**：`app/queries.py` 的 `count_actions_since`；测试 `test_count_actions_since_counts_only_window_and_action` 验证了只统计"指定用户、指定动作、指定时间之后"的记录。

### 12.2 "今天零点"是按哪个时区算的？

**这是个容易被忽略的问题。** 测试里用的是 UTC 零点，也就是北京时间早上 8 点。对中国用户来说，"每天"应该从北京时间 0 点开始算。

**解决**：按用户时区（或业务所在时区）计算零点，再转成 UTC 去查询。Redis 计数器的 key 里的日期也要用同一个时区。

### 12.3 除了 Redis 计数器，还有什么方案？

| 方案 | 优点 | 缺点 |
|---|---|---|
| 每次 COUNT 查询（现在） | 简单、准确 | 每次请求都查数据库 |
| Redis 计数器 | 极快、原子 | 多一个组件；Redis 数据可能丢失 |
| 数据库计数表 `(user_id, date, count)` | 只读一行；准确 | 高并发下同一行更新有锁竞争 |
| 令牌桶 / 滑动窗口 | 能限制突发流量（如每分钟） | 实现更复杂 |

**追问：配额和限流有什么区别？**
- **配额**：一段长时间内的总量（每天 50 次），通常是业务规则（与付费相关）。
- **限流**：短时间内的速率（每秒 5 次），是为了保护系统。
- 两者通常都需要。

## 13. 分页

### 13.1 你的分页怎么实现的？有什么问题？

用的是 `LIMIT ... OFFSET ...`。

**问题一：深分页慢**。`OFFSET 10000 LIMIT 20` 要先读出 10020 行，再扔掉前 10000 行。页数越深越慢。

**问题二：数据变化导致重复或遗漏**。用户在看第 1 页时有新文档插入，翻到第 2 页时，第 1 页的最后一条会被挤到第 2 页，重复出现。

### 13.2 怎么解决？

**游标分页（Keyset Pagination）**：记住上一页最后一条的排序值，下一页从它之后开始：

```sql
SELECT * FROM documents
WHERE user_id = ? AND (created_at, id) < (上一页最后的 created_at, 上一页最后的 id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

- 无论翻到多深，都是直接从索引定位，速度不变
- 不受新插入数据的影响
- **代价**：不能直接跳到第 N 页，只能"上一页 / 下一页"（适合无限滚动的场景）

**为什么排序要加 `id`**：`created_at` 可能有重复，只按时间排序时，时间相同的行顺序不确定，翻页时可能遗漏或重复。加上唯一的 `id` 让顺序完全确定。我们的查询函数都加了 `id` 作为第二排序键。

**为什么现在用 OFFSET**：每个用户的文档数量不多（几十到几百），OFFSET 完全够用。到需要时再改。

## 14. 测试

### 14.1 你测了什么？为什么测这些？

15 个测试，分三类：

**约束测试（`tests/test_models.py`，8 个）**——验证数据库规则真的生效：
- 新文档默认状态是 pending
- 非法状态值被 CHECK 约束拒绝
- 同一用户重复上传同一内容被拒绝；不同用户可以
- 删文档级联删 chunks；删会话级联删消息
- 同一文档不能有重复的段号
- 有文档的用户不能被物理删除

**查询测试（`tests/test_queries.py`，7 个）**：
- 权限隔离：文档列表、文档详情、按哈希查、消息列表、会话列表，各自都验证"A 看不到 B 的数据"
- N+1：会话列表只执行 1 条 SQL，且结果正确
- 配额：只统计正确的时间窗口、动作和用户

**选择的原则**：测"如果出错，后果最严重"的东西——越权是安全漏洞，N+1 是性能问题，约束失效会导致脏数据。

### 14.2 为什么用真实的 PostgreSQL 测试，不用 SQLite？

1. 我们用了 PG 特有的功能：JSONB、LATERAL、`clock_timestamp()`，SQLite 都不支持
2. 约束行为不同：SQLite 默认**不检查外键**（要手动开启）
3. 类型系统不同：SQLite 是动态类型，往整数列里存字符串也不会报错
4. **测试环境和生产环境越接近，测试越可信**

### 14.3 测试之间怎么保持独立？

每个测试都在一个事务里运行，测试结束后**回滚**（`tests/conftest.py` 的 `db` fixture）：
- 测试 A 插入的数据，测试 B 看不到
- 不需要手动清理数据
- 比每次删表重建快得多

**细节**：被测代码可能会调用 `commit()`，所以用了 `join_transaction_mode="create_savepoint"`。代码里的 commit 只会释放一个**保存点（SAVEPOINT）**，外层事务仍然可以回滚。

### 14.4 测试的表结构是怎么建的？

`engine` fixture 先删掉整个 schema 重建，然后执行 `alembic upgrade head`，**用真实的迁移建表**。这样迁移文件本身也被测试了：迁移写错了，所有测试都会失败。

### 14.5 怎么测"不应该发生的事"？

用 `pytest.raises` 断言一定会抛出某个异常：
```python
with pytest.raises(IntegrityError):
    make_doc(db, user, "renamed.md", b"same")
```

**技巧**：测试数据库约束时，故意用原生 SQL 或 Core 语句绕过 Python 层的检查，确保测的是**数据库本身**的行为（如 `test_invalid_status_is_rejected` 用原生 SQL 写入非法状态）。

### 14.6 怎么确认测试本身是有效的？

故意把被测代码改错，看测试会不会失败。比如把 `get_document` 里的 `Document.user_id == user_id` 删掉，越权测试应该失败。如果没失败，说明测试没有测到点子上。（这个思路叫"变异测试"）

## 15. 连接池与数据库运维

### 15.1 连接池大小怎么设置？

- SQLAlchemy 默认 `pool_size=5`、`max_overflow=10`，即每个进程最多 15 个连接。
- PG 默认 `max_connections=100`。
- **要算总数**：如果部署 4 个 API 进程 + 2 个 worker 进程，每个最多 15 个连接，总共 90 个，接近上限。
- **连接不是越多越好**：PG 每个连接是一个独立的后端进程，占用内存；并发查询数超过 CPU 核数太多反而更慢。
- **连接数不够时**：用 **PgBouncer** 做连接池代理，让大量应用连接共享少量数据库连接。

### 15.2 `pool_pre_ping=True` 有什么用？

每次从池里取连接前先发一个轻量的检查。如果数据库重启过、或者连接因网络问题断开了，就自动丢掉这个坏连接、换一个新的，而不是让用户请求报错。代价是每次多一次很轻的往返。

### 15.3 `ANALYZE` 和 `VACUUM` 是做什么的？

- **ANALYZE**：收集表的统计信息（行数、值的分布），优化器靠它选择执行计划。统计过时会导致选错计划。我们的 seed 脚本插入大量数据后会执行它。
- **VACUUM**：清理 MVCC 产生的死元组（被更新或删除的旧版本行），回收空间。
- **autovacuum**：PG 后台自动执行这两件事，一般不需要手动操作。但批量导入数据后，最好手动 ANALYZE 一次。

### 15.4 线上数据库出问题，从哪里查起？

1. **当前在跑什么**：`SELECT * FROM pg_stat_activity` 查看所有连接在执行什么、执行了多久、在等什么锁
2. **慢查询**：`pg_stat_statements` 找出总耗时最多的查询
3. **锁等待**：`pg_locks` 结合 `pg_stat_activity` 找出谁阻塞了谁
4. **表膨胀**：`pg_stat_user_tables` 查看死元组数量和上次 vacuum 的时间
5. **连接数**：是不是连接池耗尽了

## 16. 扩展性：数据量变大以后

### 16.1 估算一下数据量

假设 1 万用户，每人 100 个文档，每个文档 50 段：
- documents：100 万行
- chunks：**5000 万行**（最大的表），如果加上 1024 维向量（每个约 4KB），仅向量就约 200GB
- usage_logs：每人每天 50 条，一年约 **1.8 亿行**

### 16.2 usage_logs 无限增长怎么办？

1. **按月分区**：PG 声明式分区，每个月一个分区。查询自动只扫描相关分区；删除旧数据直接 `DROP` 整个分区，瞬间完成（`DELETE` 几亿行会非常慢，还会产生大量死元组）。
2. **归档**：超过保留期的数据导出到对象存储或数仓，然后删除。
3. **预聚合**：每天汇总成 `(user_id, date, count, tokens)`，明细只保留一段时间。

### 16.3 单个数据库扛不住了怎么办？

按代价从小到大：
1. **优化查询和索引**（最先做，往往效果最好）
2. **加缓存**（Redis），减少数据库读取
3. **读写分离**：一个主库写、多个只读副本读。注意**复制延迟**：刚写入的数据去从库可能读不到
4. **垂直拆分**：把 chunks / 向量放到单独的数据库或向量库
5. **水平分片**：按 `user_id` 分片到多个数据库。本项目所有数据都按用户隔离，几乎没有跨用户的查询，所以 `user_id` 是天然的分片键

## 17. PostgreSQL 与 MySQL 对比

杭州的岗位 MySQL 更常见，要准备"如果换成 MySQL 会有什么不同"。

| 方面 | PostgreSQL | MySQL (InnoDB) |
|---|---|---|
| 默认隔离级别 | 读已提交 | 可重复读 |
| 表数据存储 | 堆表，所有索引都是二级索引 | 按主键组织的**聚簇索引** |
| 二级索引的叶子节点 | 存行的物理位置（ctid） | 存**主键值**，要再查一次主键索引（**回表**） |
| 外键列 | **不自动**建索引 | 自动建索引 |
| MVCC 旧版本 | 存在表里，需要 VACUUM | 存在 undo log 里 |
| DDL 事务 | 支持，可以回滚 | **隐式提交**，不能回滚 |
| LATERAL | 支持 | 8.0.14 起支持 |
| `DISTINCT ON` | 支持 | 不支持（用窗口函数代替） |
| 部分索引 `WHERE ...` | 支持 | 不支持 |
| JSON | JSONB，支持 GIN 索引 | JSON 类型，通过生成列建索引 |
| 向量 | pgvector 扩展 | 9.0 起有 VECTOR 类型，生态不如 pgvector 成熟 |
| 幻读 | 可重复读级别下通过快照避免 | 可重复读级别下通过 **间隙锁（Gap Lock）** 和 MVCC 避免 |

### 17.1 MySQL 为什么推荐用自增主键？

因为 InnoDB 的表数据按主键顺序存储（聚簇索引）。自增主键总是在末尾追加；随机主键（如 UUIDv4）会插入到中间，导致**页分裂**，性能下降、空间浪费。

### 17.2 什么是回表？怎么避免？

在 InnoDB 里，二级索引的叶子节点存的是主键值。通过二级索引找到主键后，还要**再去主键索引里查一次**才能拿到完整的行，这就是回表。

**避免方法**：覆盖索引，让查询需要的列都在二级索引里。

### 17.3 MySQL 的间隙锁是什么？

可重复读级别下，InnoDB 不只锁住查到的行，还会锁住行之间的"间隙"，防止别的事务在这个范围内插入新行，从而避免幻读。代价是锁的范围更大，更容易产生锁等待和死锁。

### 17.4 为什么本项目选 PostgreSQL？

1. **pgvector**：向量和业务数据放在同一个库里，权限过滤和向量检索可以在一条 SQL 里完成，少维护一个组件
2. 功能更丰富：JSONB、部分索引、LATERAL、事务性 DDL
3. 索引、事务、隔离级别这些概念两者相通，面试时可以对比着讲

## 18. 本设计的已知不足

**主动说出不足并给出改进方案，比被面试官指出来好得多。**

| 不足 | 后果 | 改进方案 |
|---|---|---|
| 软删除的用户仍占用唯一的用户名和邮箱 | 注销后别人无法用这个用户名注册 | 部分唯一索引：`CREATE UNIQUE INDEX ON users (email) WHERE is_active` |
| `conversations.updated_at` 只在会话行本身被更新时才变 | 新增消息不会更新它，会话列表的排序不对 | 保存消息时在同一事务里显式更新会话的 `updated_at`（阶段 4） |
| `onupdate=func.now()` 只在通过 ORM 更新时生效 | 用原生 SQL 更新不会改变 `updated_at` | 用数据库触发器（trigger）实现 |
| `sources` 是 JSONB，没有外键 | chunk 被删后，来源指向不存在的数据 | 建 `message_sources` 关联表；或在展示时容忍缺失 |
| 分页用 OFFSET | 深分页慢，数据变化时会重复或遗漏 | 游标分页 |
| `usage_logs` 无限增长 | 表越来越大，查询和维护变慢 | 按月分区 + 归档 |
| 配额按 UTC 零点计算 | 对中国用户来说每天早上 8 点才重置 | 按业务时区计算 |
| `chunk_count` 是冗余字段 | 可能和 chunks 表的实际数量不一致 | 在同一事务里更新；或定期校对 |
| 用户名大小写敏感 | `Alice` 和 `alice` 可以同时注册 | 存储前统一转小写；或建 `lower(username)` 的唯一表达式索引 |

## 19. 开放性问题

### 19.1 如果让你重新设计，你会改什么？

可以从第 18 节里挑两三个讲。比较好的回答方式："当时这样设计是因为……，后来发现……问题，如果重来我会……"。

### 19.2 设计表的时候你的思路是什么？

1. **从需求出发**：列出所有功能，找出实体（用户、文档、会话……）和它们的关系
2. **从查询出发**：列出每个页面、每个接口要执行的查询，据此决定索引和是否需要冗余字段
3. **考虑约束**：哪些数据必须唯一、哪些不能为空、删除时子数据怎么处理
4. **考虑增长**：哪张表增长最快，需要 BigInteger、分区还是归档
5. **考虑并发**：哪些操作可能同时发生，靠什么保证正确性

### 19.3 你的服务能扛多少并发？怎么测的？

**诚实回答**：阶段一只完成了数据层，还没有做压测。可以说出计划：阶段 5 用 locust 或 wrk 对接口做压测，观察响应时间、错误率、数据库连接数，找出瓶颈。目前已知的单次查询耗时都在 0.1 毫秒以下，所以瓶颈更可能在 LLM 调用和 embedding 计算上，而不是数据库。

### 19.4 哪个查询最慢？为什么？

在当前数据量下，所有查询都在 0.1 毫秒以下。将来最慢的会是**向量检索**（阶段 4），因为要在几百万个高维向量里找最相似的，需要近似最近邻索引（如 HNSW）。

### 19.5 为什么用 Alembic 而不是手写 SQL 迁移？

手写 SQL 迁移也是可以的（比如 Flyway 就是这种方式）。Alembic 的好处是能从模型自动生成迁移草稿，以及和 SQLAlchemy 模型保持同步（`alembic check`）。但自动生成的迁移**必须审查**，本质上仍然是"人负责"。

## 20. 速查表

面试前快速过一遍：

| 关键词 | 一句话 |
|---|---|
| RESTRICT vs CASCADE | 用户→文档 RESTRICT（软删除 + 磁盘文件）；文档→段落、会话→消息 CASCADE（派生数据） |
| PG 外键索引 | PG **不会**自动给外键建索引，MySQL 会 |
| 最左前缀 | `(a,b,c)` 能用于 a / a,b / a,b,c，不能单独用于 b |
| 列顺序 | 等值在前，范围在后：`(user_id, action, created_at)` |
| 覆盖索引 | 配额查询 Index Only Scan，`Heap Fetches: 0` |
| 唯一约束 | 自带索引，chunks 不用再单独给 document_id 建索引 |
| 部分索引 | `WHERE status = 'pending'`，适合低区分度列 |
| 实测数据 | 消息查询 0.026ms vs 2.99ms；配额 0.044ms vs 1.32ms |
| N+1 | LATERAL JOIN，一条 SQL，测试断言执行次数为 1 |
| now() 的坑 | 事务开始时间，同一事务内相同；消息用 `clock_timestamp()` |
| 上传一致性 | 存文件 → 写库并提交 → 投递任务；失败要补偿；进阶用 outbox |
| 并发上传 | "先查后插"有竞态，唯一约束兜底，捕获异常或 ON CONFLICT |
| 状态机 | `UPDATE ... WHERE status = 'pending'`，检查受影响行数 |
| 任务抢占 | `FOR UPDATE SKIP LOCKED` |
| 事务里禁止 | 调用 LLM / 外部 API 等慢操作 |
| 隔离级别 | PG 读已提交；MySQL 可重复读 |
| flush vs commit | flush 发 SQL 不提交；commit 提交 |
| 自动生成迁移 | 必须审查；我们的 CHECK 约束被生成了两遍 |
| 大表加索引 | `CREATE INDEX CONCURRENTLY`，不能在事务里 |
| 权限隔离 | SQL 层 `WHERE user_id = ?`，不在 Python 里判断 |
| 403 vs 404 | 404 更安全，防止探测 id 是否存在 |
| 深分页 | OFFSET 慢，改用游标分页 `(created_at, id) < (?, ?)` |
| 测试隔离 | 事务回滚 + SAVEPOINT；用真实迁移建表 |
| 配额优化 | Redis `INCR quota:{user}:{date}` + 过期时间 |
| 分片键 | `user_id`，因为没有跨用户查询 |
