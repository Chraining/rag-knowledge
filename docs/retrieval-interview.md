# 检索评测（关键词检索、混合检索、重排序）面试题整理

> 本文档基于项目里检索评测的**实际代码和实测数据**整理。
> 这部分最有价值的地方不是"做了混合检索和重排序"，而是"做了、测了、发现没用、所以没上线，并且能说清楚为什么"。
> 面试时把这个逻辑讲清楚，比背 BM25 公式更能说明你会做工程判断。

## 0. 项目介绍话术

面试官问"你的检索效果怎么样""有没有做混合检索、重排序"时，可以这样讲（约 1 分钟）：

> 我没有凭感觉调检索，而是先搭了评测：一份是百度的公开数据集 DuRetrieval，抽了 300 个真实搜索查询和 1 万段网页；另一份是我自己造的，10 份文档、52 个问题，分成型号代码这类关键词问题和换了说法的语义问题。指标看 Recall@5 和 MRR，因为线上只把前 5 段交给模型。
>
> 然后我实现了关键词检索：jieba 分词，存进 PostgreSQL 的 tsvector 列，建 GIN 索引。这里踩了一个坑：PostgreSQL 自带的 ts_rank 只看词频、没有 IDF，Recall@5 只有 26.7%，我自己补上 IDF 加权后到了 60.8%，和标准 BM25 相当。
>
> 再用 RRF 把向量和关键词结果融合成混合检索，结果反而更差：DuRetrieval 的 Recall@5 从 80.5% 降到 75.9%，调权重也没用。我分析了原因：向量前 20 名已经覆盖了 97.1% 的相关段落，关键词这一路几乎没带来新东西，反而把好结果挤出了前 5。
>
> 重排序在自建集上把 MRR 从 0.842 提到 0.968，但前 5 段本来就全召回了，模型拿到的 5 段内容不变，回答不受影响，还要多花钱、多等一秒左右。所以最后线上保留纯向量检索，代码和评测都留着，知识库变大时可以重新评估。

**要点**：重点讲"测出来没用、为什么没用、所以不上线"。面试官很少听到候选人主动说自己做的东西没用，这恰恰是加分项。

## 1. 评测方法

### 1.1 为什么要先做评测，而不是直接加混合检索和重排序？

网上的文章都说"混合检索 + 重排序效果更好"，但效果好不好取决于你的 embedding 模型、数据和使用方式。没有评测，加了一个功能之后只能靠感觉判断，改坏了也不知道。

先有评测，每次改动都能用同一套数字比较。本项目就是最好的例子：按常识加上去的两个功能，实测一个变差、一个对线上回答没有影响。如果没有评测，就会白白上线一个更差的检索和一个每次都花钱的接口。

### 1.2 两份评测集分别是什么？为什么要两份？

| 评测集 | 内容 | 作用 |
|---|---|---|
| 自建评测集 | 10 份虚构公司的文档（制度、说明书、故障代码表、会议纪要、价格表），52 个问题，每题一个标准答案 | 贴近项目的真实用法；专门设计了关键词类问题（型号、代码），检验关键词检索是否有用 |
| DuRetrieval 子集 | 百度发布的公开中文检索数据集（C-MTEB 的一部分），300 个真实搜索查询、1 万段网页段落 | 数据量更大、问题不是我自己出的，避免"自己出题自己考" |

只用自建集的问题：题目是我出的，容易无意中出得偏向某种检索方式；而且 52 题太少，向量检索的 Recall@5 已经是 100%，再好的改进也测不出来（"饱和"）。
只用公开集的问题：和项目的使用场景不一样，而且标注不完整（见 4.4）。

### 1.3 Recall@K 和 MRR 是什么？

- **Recall@K**：相关段落中有多少比例排进了前 K 名。自建集每题只有一个答案，就是"前 K 名里找没找到"。
- **MRR**（平均倒数排名）：每个问题取"1 ÷ 第一个相关段落的排名"（第 1 名得 1 分，第 2 名 0.5 分，第 3 名约 0.33 分，没找到得 0 分），再对所有问题求平均。衡量正确答案排得靠不靠前。本项目只在前 10 名里算，10 名以后算没找到。

### 1.4 为什么最看重 Recall@5？

因为线上 Agent 每次检索把前 5 段都交给模型（`retrieval_top_k = 5`）。只要正确段落在前 5 名里，模型就能看到它；它排第 1 还是第 4，对回答影响很小。

这也是"重排序提高了 MRR 却不上线"的根本原因：MRR 衡量的是前 5 名内部的顺序，而线上用不到这个顺序。

### 1.5 评测要反复跑，怎么控制费用？

- 段落的 embedding 按内容哈希缓存在数据库里，同样的段落只调用一次 embedding 接口。1 万段第一次跑要花钱，之后改检索方式重跑是免费的。
- 重排序分数按"问题 + 段落"缓存（`rerank_cache` 表），只把缓存里没有的发给接口，每处理完一个问题提交一次，中途中断也不浪费。
- 跑付费评测之前先估算费用（之前账户欠费过一次，所以用完即停）。

## 2. 关键词检索

### 2.1 为什么要做关键词检索？向量检索有什么弱点？

向量检索比较的是"意思"，对型号、代码、人名这类没有明显语义的字符串不够敏感，例如 `E171` 和 `E117` 的向量可能很接近，但对用户来说是完全不同的两个故障。关键词检索按字面匹配，正好补这个短板。这是业界做混合检索的主要理由。

但要诚实地说：实测时 text-embedding-v4 对型号处理得已经不错，自建集里的关键词类问题向量检索也全部召回了，所以这个弱点在本项目的数据上没有体现出来。

### 2.2 jieba 是什么？分词发生在哪一步？

jieba 是一个 Python 中文分词库。英文单词之间有空格，中文没有，所以必须先把句子切成词，才能按词建立索引。

分词不是切片（chunking）。切片是把长文档切成约 500 字的段落；分词是在段落已经切好之后，把每段再切成词。发生在两个地方：

1. **写入时**：`save_chunks` 保存每段时，对段落分词，转成 `tsvector` 存进 `terms` 列。
2. **查询时**：对用户的问题分词，再去 `terms` 里匹配。

两边必须用同一个分词函数（`app/segment.py` 的 `segment`），否则同一个词切得不一样就匹配不上。

### 2.3 为什么用 `lcut_for_search`，不用普通的 `lcut`？

搜索模式会把长词里的短词也切出来，例如"路由器"会切出"路由"和"路由器"。这样用户问"路由"也能匹配到写着"路由器"的段落，召回更多。

另外只保留由字母、数字、汉字组成的词（去掉标点和空格），并统一转小写，让 `E171` 和 `e171` 能匹配上。

### 2.4 PostgreSQL 不支持中文分词，你是怎么存的？

PostgreSQL 的全文检索内置的分词规则是按空格和标点切的，不认识中文。做法是：先用 jieba 切好，用空格把词拼起来，再交给 `to_tsvector('simple', ...)`。

用 `simple` 配置是因为它只做小写转换，不做英文的词干还原（比如把 running 变成 run），也没有停用词表，不会误删中文分好的词。

### 2.5 为什么用 PostgreSQL 全文检索，不用 Elasticsearch？

- 数据库本来就是 PostgreSQL，不用多部署、多维护一个服务。服务器内存有限，Elasticsearch 光启动就要占 1GB 左右。
- 权限过滤（只搜自己的、已处理完成的文档）和检索在同一条 SQL 里完成，和向量检索的写法一样，不用在两个系统之间同步数据和权限。
- 个人知识库的数据量很小，PostgreSQL 加 GIN 索引完全够用。

如果数据量到了千万级、需要复杂的相关性调优，再考虑 Elasticsearch。

### 2.6 GIN 索引是什么？

GIN（倒排索引）记录的是"每个词出现在哪些行里"。查"包含 e171 的段落"时，直接找到 e171 这个词对应的行列表，不用逐行扫描。这和搜索引擎的倒排索引是同一个思路。

B+ 树索引适合"一行一个值"的比较和排序；tsvector 一行里有很多词，要按"包含某个词"来查，所以用 GIN。

### 2.7 ts_rank 有什么问题？你是怎么解决的？

`ts_rank` 只看词频（词在这段里出现了几次），没有 **IDF**（逆文档频率，一个词在多少段里出现过）。

后果：问"老板8218怎么样"，"怎么样"这种到处都有的词和"8218"这个关键型号权重一样，段落里"怎么样"多出现几次就能排到前面，真正提到 8218 的段落反而被淹没。

解决：自己算 IDF。先用一条 SQL 统计总段数和每个词出现在多少段里（`count().filter(...)`，一次扫描就能数出每个词），用 BM25 的公式算出 IDF：

```
idf(词) = log(1 + (总段数 - 包含这个词的段数 + 0.5) / (包含这个词的段数 + 0.5))
```

每段的得分 = 所有词的 IDF × 这个词的 ts_rank 之和。包含这个词的段越少，IDF 越大。

实测（DuRetrieval 离线计算）：

| 打分方式 | Recall@5 |
|---|---|
| 只看词频（ts_rank） | 26.7% |
| 词频再按段落长度归一化 | 28.2% |
| 标准 BM25 | 60.5% |
| IDF × ts_rank（按长度归一化，项目最终用的） | 60.8% |

结论：差距几乎全部来自 IDF，有没有 IDF 是 26.7% 和 60.8% 的区别。

### 2.8 BM25 是一个库吗？

BM25 是一个打分公式（算法），不是库。它由三部分组成：IDF（词越少见越重要）、词频饱和（一个词出现 10 次不会比出现 2 次重要 5 倍）、段落长度归一化（长段落天然包含更多词，要打折扣）。

Elasticsearch、Lucene 等搜索引擎内置了 BM25；PostgreSQL 没有内置，所以本项目用 `ts_rank`（提供词频和长度归一化）加上自己算的 IDF，拼出了一个 BM25 式的打分，效果和标准 BM25 相当（60.8% 对 60.5%）。

### 2.9 查询条件为什么用"或"（`|`），不用"且"（`&`）？

问题里有很多段落里不会出现的词，比如"怎么""什么""处理"。如果要求所有词都出现，几乎什么都搜不到。用"或"先把包含任意一个词的段落找出来（这一步用 GIN 索引），再用 IDF 加权的得分排序，常见词的贡献自然很小。

### 2.10 已经存在的段落没有 `terms`，怎么办？

在 Alembic 迁移里回填：加列和 GIN 索引之后，按 id 每 500 段一批，读出内容、用 jieba 分词、写回 `terms`。分批是为了不一次把所有段落读进内存，也不让一个事务太大。

迁移里引用了应用代码 `app.segment`，这通常不推荐（以后应用代码改了，旧迁移的行为也跟着变），这里是有意的例外，因为回填必须和线上写入用同一个分词函数，文件里写了注释说明。

## 3. 混合检索

### 3.1 RRF 是什么？

RRF（倒数排名融合）：把几个排好序的列表合并成一个。每段的得分 = 它在每个列表里的 `1 / (60 + 名次)` 之和，名次从 1 开始。

两个列表都排得靠前的段落得分最高；只出现在一个列表里的，也能凭名次排进来。本项目每一路各取 20 个候选，融合后取前 5。

### 3.2 为什么用 RRF，不直接把两个分数加起来？

两个分数的量纲完全不同：向量的余弦相似度在 0 到 1 之间，而且通常集中在 0.5 左右；IDF 加权的关键词得分没有固定范围，问题里词多分数就高。直接相加，谁的数值大谁说了算。

RRF 只看名次，不看原始分数，所以不需要做归一化，也没有要调的参数（60 是论文里的经验值，对结果不敏感）。

### 3.3 结果怎么样？

| 检索方式 | DuRetrieval Recall@5 | DuRetrieval MRR | 自建 Recall@5 | 自建 MRR |
|---|---|---|---|---|
| 向量（线上使用） | **80.5%** | **0.977** | **100%** | 0.842 |
| 关键词 | 60.8% | 0.861 | 90.4% | 0.745 |
| 混合（RRF） | 75.9% | 0.944 | 94.2% | 0.828 |

两份评测集上，混合检索都比纯向量检索差。

### 3.4 为什么混合检索反而更差？

1. **两路实力差太多**。text-embedding-v4 很强（Recall@5 是 80.5%），关键词只有 60.8%。RRF 对两路一视同仁，关键词排第 1 的错误段落和向量排第 1 的正确段落得分一样，就把向量的好结果挤出了前 5。
2. **关键词没有带来新的相关段落**。我统计了候选集的覆盖率：向量前 20 名已经覆盖了 97.1% 的相关段落；向量前 20 加上关键词前 20（去重后约 33 段）覆盖 97.8%；直接取向量前 40 名也是 97.8%。也就是说，关键词能找到的，向量多看几名也能找到。

混合检索有用的前提是"两路各有所长、能互相补充"，这个前提在本项目的数据上不成立。

### 3.5 有没有试过补救？

- **加权 RRF**：给关键词一路乘 0.25、0.5、0.75 的权重。两份评测集上所有权重都不如纯向量，权重越小越接近纯向量，但始终追不上。
- **逐条看变化**：也有被混合检索修好的例子，比如一个问"cfs 和 cy"的查询，这类缩写向量检索排不好，关键词能精确命中。但变差的查询更多，总体是亏的。

### 3.6 那 Agent 现在用的是什么？代码留着干什么？

Agent 的检索工具只用向量检索，代码里有注释说明为什么没用混合检索，并指向 README 的评测结果。

关键词检索和混合检索的代码、测试、迁移都保留：`terms` 列每次写入都会生成，以后换 embedding 模型、知识库变大、或者用户大量查询型号代码时，跑一遍评测脚本就能重新判断要不要切换。

## 4. 重排序

### 4.1 重排序和向量检索有什么区别？

- **向量检索**（双塔 / bi-encoder）：问题和段落各自转成向量，再比较向量的距离。段落的向量可以提前算好存起来，所以快，能在大量段落里检索。但问题和段落从来没有"一起读"过。
- **重排序**（交叉编码 / cross-encoder）：把问题和一段文字放在一起输入模型，直接判断相关程度。判断得更准，但每一对都要调用一次模型，又慢又花钱，只能用来给少量候选排序。

所以标准做法是两段式：先用向量检索选出 20 个候选，再用重排序模型给这 20 个重新排序，取前 5。

### 4.2 你是怎么接入的？

用阿里云百炼的 `qwen3-rerank`。这个接口不兼容 OpenAI 格式，所以没用 openai 库，而是直接用 HTTP 库发请求（项目里用 openai 库依赖的 `httpx2`，不新增依赖）。

- 接口返回的结果是按分数从高到低排的，每项带着它在输入里的位置 `index`，代码按 index 放回输入的顺序。
- 网络错误、超时、错误状态码（比如欠费返回 400）、返回格式不对，统一转换成项目自己的 `LLMUnavailable` 异常，和 embedding、对话接口的错误处理方式一致。
- 测试里用假的 HTTP 响应，不联网、不花钱。

### 4.3 重排序提升了 MRR，为什么不上线？

| 方式 | 自建 Recall@1 | 自建 Recall@3 | 自建 Recall@5 | 自建 MRR |
|---|---|---|---|---|
| 向量 | 73.1% | 92.3% | 100% | 0.842 |
| 向量 + 重排序 | 94.2% | 100% | 100% | **0.968** |

重排序在自建集上确实有效：正确段落排第 1 的比例从 73.1% 提高到 94.2%，关键词类问题的 MRR 达到 1.0。

但是 Recall@5 本来就是 100%：重排序只是把正确段落在前 5 名里往前挪，而 Agent 把前 5 段全部交给模型，模型拿到的内容几乎没变，回答也就不变。代价是每次检索多花约 0.005 元、多等约 0.5 到 1 秒。花钱、变慢、没有收益，所以不上线。

### 4.4 DuRetrieval 上为什么持平？

DuRetrieval 上 Recall@5 是 79.6%，向量是 80.5%，基本持平：34 个查询变好，31 个变差。

我逐条看了变差的查询，分成两类：

1. **重排序真的排错了**：被字面相同的词误导。比如问"bjd 娃娃"（一种球形关节人偶），它把一条奶瓶的评价排了上来，因为里面有"娃娃"；问护肤品的"霜"，排上来一段讲红枣表面"白霜"的文字。
2. **数据集标注不全**：它排上来的段落其实是相关的，只是数据集没有把它标成正确答案，所以算作"变差"。还发现一个标注问题：问"老板8218"的查询，标注的正确段落里根本没有"8218"。

结论：公开数据集的标注不完整，排序上的小差别会被标注噪声淹没，所以不能只看一个数字，要逐条看。

### 4.5 为什么不直接用 DeepSeek 这种大模型做重排序？

- **贵**：大模型按 token 收费，20 段候选每段约 500 字，一次重排序就要上万 token，比专用的重排序模型贵很多。
- **慢**：大模型要生成文字，比只输出分数的重排序模型慢得多，用户等待时间更长。
- **不稳定**：要让模型输出分数或排序结果再解析，可能格式不对、漏掉段落、每次结果不一样。
- **没必要**：专用的重排序模型已经测过，对线上回答都没有影响，换成更贵的大模型也解决不了"前 5 段已经全召回"这个根本问题。

### 4.6 什么时候值得上线重排序？

1. **知识库变大**：段落多了以后，向量检索的 Recall@5 会明显低于 100%，这时把正确段落从第 8 名挪进前 5 名就有实际价值。
2. **想少给模型几段**：如果想只给模型 3 段以缩短提示词、降低费用，重排序把自建集的 Recall@3 从 92.3% 提高到 100%，这时就值得用。

上线前还是先跑评测，用数据决定。

## 5. 反思与追问

### 5.1 花时间做了两个最后没上线的功能，是不是白做了？

不是。

1. 得到了一个可靠的结论：在当前的模型和数据下，纯向量检索就是最优的。没有评测的话，很可能按"常识"上线了一个更差的混合检索。
2. 评测脚本、关键词检索、重排序的代码都留着，条件变化时（换模型、数据变多）跑一遍就能重新判断。
3. 过程中发现了 ts_rank 没有 IDF 这种只有动手才会遇到的问题。

### 5.2 你的评测有什么局限？

- **只测了检索，没有测回答**。检索对了，模型也可能答错；检索排序变了，回答不一定变。回答级的评测（用另一个模型当裁判给回答打分，LLM-as-judge）还没做。
- **自建集已经饱和**。向量检索的 Recall@5 已经是 100%，后续的检索改进在这份评测集上测不出来，需要更大、更难的评测集。
- **公开数据集标注不全**，小幅度的差别不可信（见 4.4）。
- **评测数据和真实用户的问题不一样**。项目上线时间短，还没有真实的用户问题日志可以用来评测。

### 5.3 如果继续做，下一步做什么？

1. 回答级评测：对每个问题让模型生成回答，再让另一个模型对照标准答案打分，衡量的是用户真正关心的回答质量。
2. 扩大自建评测集，加入更多文档、更难的问题，让检索的改进能测得出来。
3. 收集线上的真实问题（不记录用户隐私内容），作为最接近真实情况的评测集。

### 5.4 混合检索为什么在很多文章里都说有用，你这里却没用？

文章里的对比通常用的是较弱的 embedding 模型，或者数据里有大量专有名词、代码。两路检索的实力相近、各有所长时，融合才会互补。

本项目用的 text-embedding-v4 本身很强，关键词一路明显更弱，也没有带来新的相关段落。所以"有没有用"取决于具体的模型和数据，不能照搬结论，这正是要自己做评测的原因。
